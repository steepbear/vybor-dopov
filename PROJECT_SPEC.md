# Дополнение к спецификации: олимпиады как допы — V4

- Все направления, включая олимпиады, имеют группы с `id`, `subject`, `group`, `branchId`, `grade`, `sessions`, `type`. Тип `regular` либо `olympiad`; отсутствие типа у исходных обычных групп интерпретируется как `regular`.
- Предложение олимпиады — ссылка `olympiadOffers[studentId] = groupId`, а не собственная копия времени.
- Методолог сначала создаёт группу олимпиады в каталоге своего филиала и параллели, затем предлагает её ученикам. Ученик может принять или отклонить предложение.
- Олимпиада без персонального предложения не показывается ученику; принятие блокируется при пересечении с его обычными допами.
- Группа с предложениями или выборами защищена от удаления/изменения расписания.
- Один ученик пока получает не более одного активного предложения олимпиады (ограничение демо, расширяемая модель).
- Существующие демо-предложения нормализованы в реальные группы; локальные V3-предложения по времени мигрируют к группам при загрузке.
- Филиал методолога и параллели изолированы (в демо нет реальной авторизации и общей БД).

# Выбор допов — спецификация V3, 25.10.2026

## Подтверждённая логика

1. Филиал — самостоятельная школа. Обычный методолог привязан **строго к одному филиалу**, администрирует внутри него параллели 1–4; ученики и группы других филиалов недоступны. В демо есть переключатель кабинета без настоящей аутентификации.
2. Общие **направления** («Карате», «Астрономия» и т. д.) могут переиспользоваться несколькими филиалами/параллелями. Конкретные **группы и расписания** — в паре (`branchId`, `grade`).
3. Основной сценарий — **ручной выбор группы** учеником. Одна группа на направление (текущее допущение интерфейса). Не ограничивать число направлений. Единственное ограничение подбора — отсутствие пересекающихся временных слотов у конкретного ученика.
4. Олимпиада — необязательное направление по персональному **предложению** методолога. Предложение содержит слоты, доступно только указанному ученику. Ученик принимает сам; без согласия слот не блокирует выбор других занятий. После согласия пересечения проверяются так же, как с группами.
5. После подтверждения выбор нельзя менять из кабинета ученика; методолог может снять подтверждение. Нельзя править/удалять группу, выбранную учеником; нельзя править/отзывать принятое предложение олимпиады, пока ученик не изменит своё решение.
6. Отчёты на уровне филиала и параллели: неподтверждённые ученики, выборы по направлениям, группам, классам; в подсчётах подтверждённых — только подтверждённые записи.
7. Необязательный помощник подбирает максимум совместимых направлений с учётом приоритетов; не меняет результаты без согласия ученика.

## Демо-модель V3

Базовые `DATA.students`, `DATA.groups`, `DATA.olympiadOffers` живут в `data.js` (синтетические/учебные данные). В `localStorage` приложения `vybor_dopov_demo_v3` записываются:

- `addedStudents`: добавленные через веб-интерфейс ученики;
- `groupOverrides`: добавленные, изменённые и удалённые (`null`) группы;
- `offerOverrides`: новые/изменённые/отозванные (`null`) предложения олимпиады отдельным ученикам;
- `records`: выбранные группы, принятие олимпиады, подтверждение.

При запуске `app.js` собирает действующие списки из `data.js` и локальных изменений, строит индексы, показывает ученику каталог только его `branchId`/`grade`.

Редактирование в интерфейсе не затрагивает файлы репозитория. Любые права на данные в статическом приложении имитируются, их нельзя считать защитой от доступа.

## Будущая БД (для многопользовательской версии)

`Branch`, `Methodologist(branch_id)`, `Student(branch_id, grade, class_letter)`, `Subject`, `Offering(subject_id, branch_id, grade, academic_year)`, `Group(offering_id, group_no)`, `GroupSession(group_id, day, start_time, end_time)`, `OlympiadOffer(student_id, status)`, `OlympiadSession(offer_id, day, start_time, end_time)`, `Selection(student_id, confirmed_at)`, `SelectionGroup`, `AuditLog`.

Сервер должен атомарно проверять: принадлежность редактируемой записи филиалу методолога; соответствие группы филиалу и параллели ученика; отсутствие временных конфликтов внутри личного расписания; защиту подтверждённых записей при изменении расписания; права на создание/отзыв олимпиад. Историю изменения расписаний сохранять в аудите.
