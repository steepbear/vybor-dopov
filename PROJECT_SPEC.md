# Выбор допов — проектные решения V2 (25.10.2026)

## Утверждённые правила

1. Основной сценарий — самостоятельный **ручной выбор конкретных групп** учеником.
2. Максимального количества направлений нет; ограничение — отсутствие пересечений выбранных занятий в расписании ученика.
3. **Филиал** — самостоятельная школа со своими учениками, методологами, предложениями занятий, группами и расписанием.
4. **Параллель** (1, 2, 3, 4) — независимая учебная область внутри филиала. Ученику доступны только группы **его филиала и его параллели**.
5. Названия направлений и их описания — единый переиспользуемый справочник: «Карате» может быть доступно одновременно в 1, 2 и 4 параллелях, но это отдельные предложения, группы и расписания.
6. **Проверка временных пересечений** применяется только к выбору отдельного ученика среди его групп (и принятой олимпиады) внутри его филиала и параллели. Между параллелями или филиалами **не блокируем одинаковые часы**.
7. Олимпиаду могут предложить конкретным ученикам. Ученик решает принять/не принять; после принятия её время учитывается при подборе и проверке пересечений.
8. Конфликтующие по времени группы видны, но недоступны, с причиной блокировки.
9. Подтверждённый выбор заблокирован для ученика; методолог может открыть изменение. В демо переключатель ролей без реальных полномочий.
10. Необязательный помощник предлагает совместимые группы по желаниям с учётом приоритетов, но не отменяет ручной выбор.
11. Отчёты методолога: без подтверждения; по направлениям, группам, классам **в контексте выбранных филиала и параллели**.
12. Демонстрационный запуск — GitHub Pages без аккаунтов и серверной базы, с синтетическими учениками.

## Логическая модель будущей БД

- `Branch(id, name)` — филиал/школа.
- `Methodologist(id, ..., branch_id)` — методолог принадлежит филиалу; контроль филиала обеспечивается серверными правами.
- `Student(id, branch_id, grade, class_letter, ...)` — ученик одного филиала и параллели.
- `Subject(id, name, description)` — общий справочник дополнительных направлений (без привязки к школе).
- `Offering(id, branch_id, grade, subject_id, school_year, published)` — предложение предмета для **конкретных** филиала и параллели.
- `Group(id, offering_id, group_no, ...)` — группа внутри предложения.
- `GroupSession(id, group_id, weekday, start_time, end_time)` — часы и дни занятий группы.
- `OlympiadOffer(id, student_id, school_year, status, ...)` и `OlympiadSession(olympiad_offer_id, weekday, start_time, end_time)` — персональное предложение, принятие/отказ, расписание.
- `Selection(id, student_id, school_year, confirmed_at, ...)` и `SelectionGroup(selection_id, group_id)` — группы подтверждённого или текущего выбора.
- `AuditLog(actor_id, action, timestamp, ...)` — изменения со стороны методолога.

Ключевой инвариант: `Group -> Offering -> (Branch, Grade)` всегда совпадает с `(Branch, Grade)` студента в `Selection`. Для методолога — только филиалы из его прав доступа. Ограничения нельзя надёжно обеспечивать только фильтрацией HTML: при переходе на настоящую базу проверять их на сервере/в транзакции.

**Пересечение**: временные интервалы `[start,end)` двух записей одного дня перекрываются. В V2 демо исходная модель использует два фиксированных слота, поэтому проверка работает по `(день, слот)`. Позднее можно перейти на произвольное время.

Не проверяем перегруженность помещений и преподавателей между разными параллелями: это отдельное возможное правило, не включённое в текущие требования.

## Что реально работает в V2

- Ученик: выбор **филиала → параллели → учебного ученика**, список доступных групп только в этом контексте, выбор, замена, конфликт, олимпиада, расписание, подтверждение, помощник.
- Методолог: выбор **филиала → параллели**, отчёты только по ней, список групп и их расписаний, снятие подтверждения.
- Все выборы и подтверждения хранятся в `localStorage` текущего браузера; другой браузер их не увидит.
- Отсутствует настоящая авторизация, управление правами, редактирование самих групп, живая БД, импорт новой школы.

## Учебные данные и отличие от Excel

В исходном Excel: **54 учебных ученика 2-й параллели**, 3 филиала, 16 направлений, 28 групп с 46 занятиями и олимпиады. **В исходном расписании групп нет принадлежности к филиалу.**

Чтобы показать структуру, V2 создаёт для 2-й параллели **копию каждого шаблона группы в каждом из трёх филиалов**. Это не подтверждённое реальное распределение. Для параллелей 1, 3, 4 созданы по одному полностью вымышленному ученику и четыре учебные группы в каждом филиале (9 учеников и 36 групп в сумме). Итого в демо — 63 ученика и 120 отдельных групп (из них 84 для второклассников).

Перед реальным использованием методолог должен указать, какой предмет и какая группа существует в какой параллели и филиале; демонстрационные дубликаты не переносить в рабочую базу как факт.

## Открытые вопросы

- Для одного направления ученик может выбрать одну группу (допущение демо) или несколько?
- У методолога ровно один филиал или нужна возможность вести несколько филиалов?
- Как будем администрировать создание/изменение `Offering`, групп и расписаний, и импорт из Excel?
- При изменении групп после подтверждения нужна политика уведомления, проверки конфликтов и повторного подтверждения.
