# Выбор допов — V7: администратор и учётные записи

Сайт для GitHub Pages + существующая база V6 + серверная Supabase Edge Function `school-accounts`.
Это **надстройка над V6**, а не новая база: исходные таблицы и записи не удаляются.

## Что изменилось

- `index.html`: две формы входа — сотрудник по email/паролю, ученик по логину/паролю. Системный администратор автоматически переходит в `accounts.html`.
- `accounts.html`: системный администратор создаёт филиалы и методологов, сбрасывает их пароли и блокирует доступ. Методолог создаёт/привязывает ученические учётные записи, сбрасывает пароль и блокирует доступ строго в своём филиале.
- Ученический логин: `Иванов Иван` → `IvanovI-001` (следующие коллизии по номеру 002, 003…). **Только тесты и демонстрации.** ФИО вводится и преобразуется в браузере, сервер получает основу логина `IvanovI`, класс и параллель. Новый `students.full_name` заполняется логином, а не ФИО.
- Ученический пароль: слово латиницей длиной 4–6 символов + четыре цифры, например `lipa4827`. Пароль показывается однократно при выдаче/сбросе, старый пароль узнать нельзя. Хранение хеша выполняет Supabase Auth.
- Технический внутренний email для Supabase Auth создаётся на сервере, случайный и не связанный с ФИО. Ребёнок не вводит и не знает email; его действующая сессия передаётся из защищённой Edge Function в клиент Supabase.
- Есть локальная CSV-выгрузка ФИО ↔ логин из текущей сессии браузера; она не отправляется в Supabase. Данные из памяти страницы очищаются при обновлении.
- Старым ученикам V6 **без учётной записи** доступна кнопка «Выдать доступ»; при этом `full_name` заменяется на логин. Ранее созданные EMAIL-учётки учеников с существующим `user_id` автоматически не конвертируются.

## УСТАНОВКА (по порядку)

### 0. Сохранить резервную копию

Перед SQL сделать копию базы. Не запускать в рабочей базе с реальными учениками без ревизии требований к персональным данным.

### 1. SQL-миграция

В существующем Supabase, где уже выполнены шаги V5/V6, открыть **SQL Editor** и выполнить весь файл `01_v7_accounts.sql`.
Ожидаемый результат — успешное создание `student_accounts`, `profiles.is_active`, функций ограничений входа и RLS-политик. Старая база остаётся на месте.

### 2. Первый системный администратор — однократно

1. Supabase → **Authentication → Users → Add user**. Создать **отдельную** тестовую учётную запись с email и надёжным паролем. **Не менять роль существующего методолога!**
2. Открыть `02_bootstrap_admin_TEMPLATE.sql`, заменить `ADMIN_EMAIL_HERE` на email нового администратора.
3. Выполнить SQL через SQL Editor. В результате должна появиться строка `system_admin`.
4. Дальше школы и методологи создаются **через интерфейс**, не через SQL.

### 3. Edge Function (обязательный шаг)

Сам сайт GitHub Pages не может безопасно создавать учётные записи через Admin API.
Развернуть Edge Function с **точным названием `school-accounts`** и кодом `supabase/functions/school-accounts/index.ts`.

**Через Supabase Dashboard:** Edge Functions → Deploy a new function / Create function → вставить весь `index.ts` → Deploy. В настройках функции **отключить legacy Verify JWT**. Это НЕ отключает проверку пользователей: в коде явно проверяются действительный токен Supabase и роль пользователя для всех защищённых действий. Открыта только операция `login_student`, у неё есть ограничение попыток входа. При необходимости установить секрет `V7_ALLOWED_ORIGINS=https://steepbear.github.io` (это значение используется по умолчанию).

**Через Supabase CLI:** файл `supabase/config.toml` уже содержит:

```toml
[functions.school-accounts]
verify_jwt = false
```

Развёртывание: `supabase functions deploy school-accounts --no-verify-jwt` после `supabase login` и `supabase link --project-ref <ваш project-ref>`.

Ключи `SUPABASE_SECRET_KEYS` и `SUPABASE_PUBLISHABLE_KEYS` Supabase предоставляет Edge Function через окружение. `sb_secret_...` и `service_role` **никогда** не записывать в JS на GitHub и не вводить на сайте.

**Важно:** настройка Supabase Auth по умолчанию может отклонять служебные домены `.invalid` при отдельных конфигурациях валидации email. Если создание тестовой учётки выдаст ошибку email, сначала исправить технический домен в Edge Function на **специальный домен, контролируемый вашей организацией**; не переходить на реальные email учеников.

### 4. Обновить GitHub Pages

В корне репозитория заменить `index.html`, `app.js`, `style.css`, `live.css` (два CSS — текущие из V6 с дополнениями). Добавить `accounts.html`, `accounts.js`, `accounts.css`.

**Не загружать** в корень GitHub: SQL-файлы, Edge Function, `.env`, секреты или CSV-сопоставления реальных детей. SQL и Edge код рекомендуется держать в закрытом репозитории разработчика.

### 5. Приёмочные проверки (вымышленные ученики)

1. Войти под `system_admin` с email и паролем — перенаправление на `accounts.html`.
2. Убедиться, что филиал «Крымская» отображается. При желании создать второй тестовый филиал.
3. Создать нового методолога и зафиксировать одноразово выданный пароль. Выйти.
4. Войти методологом — открыть «Управление учётными записями».
5. Ввести «Иванов Иван» → должно получиться `IvanovI`. Создать ученика 2 «А» и получить логин с номером, пароль формата `слово1234`.
6. Выгрузить локальный CSV «ФИО — логин» и проверить, что он **не появляется в Supabase**.
7. Выйти и войти на `index.html` в режиме «Ученик» по логину и паролю. Проверить доступные группы, выбор, олимпиады и подтверждение из V6.
8. Снова войти методологом, сбросить ученический пароль: старый не должен работать. Проверить блокировку и разблокировку.
9. Убедиться, что методолог одного филиала не видит и не может сбрасывать аккаунты другого.

## Важные ограничения

- **V7 не развёрнута автоматически**. Тесты выполнены локально с имитацией Supabase API. Исполнение SQL и Edge Function в вашей живой базе пока не проверено.
- В V7 не реализовано редактирование существующих направлений, групп и расписаний: это задача V8, требующая проверки конфликтов для уже записанных учеников.
- Простой пароль + угадываемый логин допустимы лишь для демонстрации с вымышленными данными. Есть серверное ограничение по попыткам входа (15-минутное окно), но перед реальным внедрением нужна полноценная проверка безопасности, защита Auth API, дополнительная антибот-защита и аудит.
- Логин `IvanovI-001` содержит данные, позволяющие предположить имя человека. Это **не полноценное обезличивание**. В старых записях `students.full_name` могли остаться ФИО; миграция их не удаляет, чтобы случайно не испортить данные.
- Технические email хранятся во внутреннем `auth.users` Supabase; реальный email/телефон ученика не требуется.
- Сайт по-прежнему размещён на GitHub Pages, данные — в Supabase. Это **не автономная коробочная установка**. Для коробки потребуется отдельное развёртывание сервера и PostgreSQL, установщик и резервное копирование.
- Предназначено для технической проверки на вымышленных данных. Не переносить персональные данные детей в европейский Supabase без отдельной правовой оценки.
