# Выбор допов — архитектура V9 (утверждено 12.11.2026)

> V9 разрабатывается в основной ветке `main`; V8 — только источник существующего кода и механик. Это описание целевого состояния, не описание уже применённой схемы Supabase.

## 1. Справочники

- **Ученик**: постоянный UUID/GUID, филиал, привязанная учётная запись, неизменный логин. Фамилия и имя **не хранятся в Supabase**. ФИО присутствуют только в локальном школьном реестре `.vdop`.
- **Доп (направление)**: постоянный UUID/GUID, название. Создаётся один раз, не закрепляется за параллелью.
- **Филиал**: постоянный UUID/GUID и название.
- **Учебный год**: значение года начала, например `2026` означает `2026/2027`. Отдельный справочник лет не обязателен.

## 2. Документ «Класс»

Уникальность документа: **(учебный год, филиал, параллель 1–4, буква класса)**. Например 2026/2027 — Крымская — 2 — А.

Состав (табличная часть): GUID учеников. Один ученик может состоять не более чем в одном классе данного филиала **в рамках одного учебного года**. Идентичность ученика от класса не зависит.

Статусы: **Формируется → Активен → Завершён**. Завершённые документы и история сохраняются; изменения состава после завершения по умолчанию запрещены.

## 3. Документ «Расписание допов»

Уникальность: **(учебный год, филиал)**. Статусы аналогичные.

Табличная часть включает **группы** с указанием постоянного GUID допа, типа (обычный доп / олимпиада), имени группы и временных слотов.

- У одного допа может быть несколько групп одного филиала.
- Параллель — необязательное ограничение **группы**, а не допа: пустой набор означает 1–4, указанное множество — только выбранные параллели (например 1 и 2).
- При проверке пересечений учитывать выбранные группы обычных допов и принятых олимпиад.

## 4. Выбор ученика

Связывает постоянный GUID ученика и группу из документа расписания **того же учебного года и филиала**. Перед записью проверяются зачисление в документ класса, доступность группы по параллели, пересечения, срок выбора, подтверждение, статус документов.

Подтверждение выбора, включая пустой выбор по отдельно установленным правилам, должно храниться **в разрезе учебного года**, не в постоянной карточке ученика.

## 5. Массовый перевод

Раздел методолога: **«Учебный год»**.

1. Выбрать исходный и целевой годы для своего филиала.
2. Сформировать соответствия документов класса (1А → 2А, 2А → 3А, 4А → Выпуск); просмотреть составы.
3. Допустить индивидуальные исключения: другой класс, повтор года, выбытие.
4. Предварительная проверка: уникальность целевых документов и отсутствие повторного зачисления в целевом году.
5. После подтверждения — записать зачисления в документы целевого года; прежняя история неизменна. Завершать исходные документы **явным отдельным действием**, чтобы не блокировать проверку частичного перевода.
6. Постоянный GUID, логин, пароль ученика не изменять; назначения допов следующего года не копировать.

Повторное проведение перевода — идемпотентное (не создаёт повторных зачислений).

## 6. Локальный реестр зачисления .vdop V2 (утверждено 17.11.2026)

**Создание ученика не означает зачисление в конкретный класс.** Сначала школа принимает ребёнка, затем создаёт документы классов учебного года и распределяет учеников.

- При приёме фиксируются постоянный UUID, филиал, год первоначального зачисления и учётная запись. Поля grade и class_letter не заполняются.
- Локальный файл .vdop содержит ФИО. Ни одна операция регистрации/распределения не отправляет их в Supabase.
- Формат файла: заголовок VDOP/2, данные format, version=2, kind=school_admissions, registry_id, branch_id, branch_name, admission_year, students[].
- Строка: id (GUID), surname, name, login (пуст до регистрации), namesake_verified (локальное подтверждение совпадающих ФИО). Нет параллели и буквы класса.
- Excel при создании реестра требует только «Фамилия» и «Имя». Поле «Класс», если присутствует, игнорируется. Файл не загружается напрямую в базу.
- Повтор GUID — ошибка. Совпавшие ФИО — предупреждение, требующее подтвердить локально, что это разные дети, прежде чем сохранить/зарегистрировать.
- При «Создать из Excel» действуют согласованные условия полной замены с диалогом «Текущие данные будут заменены данными из файла. Продолжить?». Неудачное чтение не стирает старый реестр.
- Прежний V1 можно открыть как конвертацию в V2: класс удаляется из нового файла, старый исходник на устройстве не изменяется.
- Перед регистрацией школа **сохраняет .vdop с GUID**, после выдачи логинов снова сохраняет обновлённый .vdop.
- Пароли никогда не сохраняются в .vdop: однократно выгружаются в XLSX с ФИО, логином и паролем (собирается только в браузере).

## 7. Логины и регистрация

Формат для новых учеников: **2026_Ф1_Ученик_0001**. Год — год первоначального зачисления, Ф1 — стабильный цифровой код филиала, 0001 — следующий свободный номер в рамках года и филиала.

- Филиал получает постоянный v9_code (Ф1, Ф2 и т. д.).
- Постоянный GUID уже назначен в локальном .vdop; сервер не генерирует новый.
- Повторная отправка GUID возвращает ранее выданный логин без создания второго аккаунта (пароль повторно не выдаётся).
- Логин неизменен при переводе между классами и годами. Старые логины V8 не переименовываются.
- Ученик может существовать без классного документа.
- Методолог видит ФИО только после открытия локального .vdop, распределяет строки по документам своего филиала. В базу идут только GUID и ссылки на документы.

## 8. Порядок реализации

1. Локальный редактор .vdop V1 (завершён ранее).
2. Документы классов, год/филиал/параллель/буква, статусы и членство (завершено).
3. Зачисление без класса, .vdop V2, массовая регистрация и массовое распределение по документам (внедряется).
4. Документ расписания на год, независимые допы и группы с опциональной параллелью.
5. Перенос выбора, олимпиад и сроков, массовый перевод на следующий год.
6. Сквозные тесты V9; удаление оставшихся старых V8-сценариев.

## 9. Реализация V9: этап 2 (13.11.2026)

**Выполнено и применено в Supabase:** таблицы `v9_class_documents` и `v9_class_enrollments`; SQL определения хранятся в `supabase/migrations/v9_class_documents.sql`.

- Документ класса: один на уникальные значения (филиал, год, параллель, буква), статусы `draft → active → finished`.
- Состав класса: ссылки на постоянные GUID из `students`, без ФИО.
- Уникальность (филиал, учебный год, GUID ученика) не позволяет назначить ученика в два класса в один год.
- Внешние ключи защищают от зачисления чужого ученика в другой филиал или несоответствия году документа.
- После завершения документа запрещено менять его статус или состав.
- RLS: только методолог собственного филиала читает и изменяет документы и состав.
- Интерфейс `v9-classes.html` — создание документов, выбор года и параллели, зачисление уже зарегистрированных учеников, удаление из состава, активация и завершение.
- На странице методолога `index.html` есть ссылка «Учебный год · Документы классов V9».

**Дальнейшая интеграция:** регистрация GUID из .vdop V2 и массовое распределение реализуются отдельно. Старый выбор допов пока опирается на V8 поля students.grade и старые группы.

## 10. Реализация V9: этап 3 (17.11.2026)

- Обновляется схема: branches.v9_code, допускаются NULL в students.grade и students.class_letter; ограничение на логин принимает кириллические идентификаторы.
- Edge Function school-accounts поддерживает v9_admit_students: до 5 UUID за запрос, авторизация методолога и проверка филиала, идемпотентность по GUID. В запросах нет ФИО.
- Редактор v9-registry.html использует .vdop V2: приём учеников без класса, регистрация по GUID, повторное сохранение файла, разовая выгрузка учётных данных в XLSX.
- Документы классов массово пополняются из локального .vdop через v9-classes.html, с контролем незарегистрированных/уже распределённых GUID.
- Старую массовую загрузку XLSX напрямую в Supabase скрыли из главного интерфейса методолога. Excel — только для создания локального .vdop.
- Выбор допов V8 ещё не переведён на связи V9, наличие ученика без класса не даёт ему права выбирать занятия.
